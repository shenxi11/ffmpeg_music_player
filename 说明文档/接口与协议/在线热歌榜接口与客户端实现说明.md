# 在线热歌榜接口与客户端实现说明

更新时间：2026-04-18

## 1. 背景与目标

服务端已经落地“在线热歌榜”能力。客户端本次只做接入，不改服务端协议。

本次客户端 v1 目标固定为：

- 展示一个公开可见的“在线热歌榜”页面
- 默认展示最近 30 天的前 20 首在线热歌
- 支持切换 `7d / 30d / all` 三个统计周期
- 榜单歌曲沿用现有在线歌曲播放、收藏、下载、加入歌单、评论入口链路
- 未登录用户可浏览榜单，写操作仍遵守现有登录限制
- 同时兼容服务端曲库歌曲和 Jamendo 在线歌曲

不做的内容：

- 不做多榜单体系
- 不做榜单详情页
- 不做客户端本地热度计算
- 不改服务端热度统计规则
- 不新增独立播放器或独立歌曲数据模型

## 2. 服务端已落地接口

### 2.1 获取在线热歌榜

`GET /music/charts/hot?window=30d&limit=20`

说明：

- `window` 可选，枚举值为 `7d`、`30d`、`all`
- 服务端默认 `window=30d`
- `limit` 可选，范围 `1..100`
- 服务端默认 `limit=20`
- 返回的是“在线音乐”热度榜，不包含本地离线歌曲
- 当前榜单由 Redis 排行榜提供，不是客户端本地排序

典型响应：

```json
{
  "chart_id": "online-hot-30d",
  "title": "在线热歌榜",
  "window": "30d",
  "generated_at": "2026-04-18T15:48:05+08:00",
  "items": [
    {
      "rank": 1,
      "music_path": "七里香/七里香.mp3",
      "path": "七里香/七里香.mp3",
      "title": "七里香",
      "artist": "周杰伦",
      "album": "七里香",
      "duration_sec": 299,
      "cover_art_url": "http://127.0.0.1:8080/uploads/covers/qilixiang.jpg",
      "source": "catalog",
      "source_id": "catalog:七里香/七里香.mp3",
      "play_count": 47
    }
  ]
}
```

顶层字段：

- `chart_id`
- `title`
- `window`
- `generated_at`
- `items`

其中 `items` 每一项至少包含：

- `rank`
- `music_path`
- `path`
- `title`
- `artist`
- `album`
- `duration_sec`
- `cover_art_url`
- `source`
- `source_id`
- `play_count`

### 2.2 失败响应语义

常见状态码：

- `200`：成功
- `503`：Redis 榜单当前不可用

客户端必须区分：

- `200 + items=[]` 表示真实空榜单
- `503` 表示榜单服务暂不可用，不能渲染成空榜单

## 3. 服务端真实行为与客户端注意事项

### 3.1 热度统计来源

服务端当前统计规则是：

- 每次在线歌曲成功写入一次播放历史
- 对应热歌榜热度 `+1`

也就是说，热歌榜统计的不是：

- 客户端本地播放次数
- 前端页面点击次数
- 拉流开始次数

而是：

- 服务端成功处理 `/user/history/add` 后的在线播放历史写入次数

客户端不需要额外上报“热度”接口，只要继续保持现有在线歌曲播放历史上报链路正常即可。

### 3.2 只统计在线歌曲

服务端热歌榜只统计在线歌曲，当前可兼容两类路径：

- 服务端曲库相对路径，例如 `七里香/七里香.mp3`
- Jamendo 虚拟路径，例如 `Mayday [jamendo-1431925].mp3`

不支持：

- Windows 本地绝对路径
- `file:///` 本地路径
- 客户端私有缓存路径

因此客户端榜单页必须把热歌榜视为“在线歌曲榜单”，不要混入本地音乐。

### 3.3 `source` 字段必须保留

服务端当前会返回：

- `source=catalog`
- `source=jamendo`

客户端不要因为 `music_path` 形态不同就自行推断来源，更不要丢弃 `source` 和 `source_id`。这两个字段后续可用于：

- 来源区分
- 日志排障
- 评论/播放/搜索联动时的问题定位

### 3.4 服务端已经排序完成

`items` 已经是按热度倒序返回，并带有 `rank`。

客户端不要：

- 再按 `play_count` 二次重排
- 用本地排序覆盖服务端排名
- 在不同 `window` 之间尝试本地推导排名

周期切换后应重新请求服务端。

## 4. 客户端 v1 接入建议

### 4.1 页面形态

客户端 v1 建议新增一个独立的“在线热歌榜”页面，作为在线发现/推荐链路下的一个固定页面，而不是把榜单塞进搜索结果页。

展示规则固定为：

- 页面头部显示榜单标题和周期切换
- 主体区域显示前 20 首歌曲列表
- 列表项展示排名、封面、标题、歌手、可选专辑名、热度值

建议周期切换固定三项：

- `近7天`
- `近30天`
- `总榜`

默认首屏请求：

- `GET /music/charts/hot?window=30d&limit=20`

### 4.2 推荐接入层级

网络层：

- `src/network/httprequest_v2.*`
- 新增热歌榜请求方法和响应解析

ViewModel 层：

- `src/viewmodels/MainShellViewModel.*`
- 对外透传热歌榜成功/失败信号

页面/UI 层：

- 优先复用 `src/ui/widgets/library/` 下的在线歌曲列表模式
- 可参考 `RecommendMusicWidget` 的页面组织和刷新行为
- 不建议单独再造一套“榜单专用播放模型”

### 4.3 推荐网络接口形态

建议在 `HttpRequestV2` 新增：

- `getHotMusicChart(const QString& window = QStringLiteral("30d"), int limit = 20);`

建议新增成功信号：

- `signalHotChartResult(bool success, const QVariantMap& meta, const QVariantList& items, const QString& message, int statusCode, const QString& window);`

也可以采用现有推荐接口风格拆成两组信号，但建议至少保证：

- 成功时能拿到 `meta + items`
- 失败时能拿到 `message + statusCode + window`

### 4.4 推荐 ViewModel 透传形态

建议 `MainShellViewModel` 只做轻量转发：

- 成功：`emit hotChartReady(meta, items);`
- 失败：`emit hotChartRequestFailed(message, statusCode, window);`

如果客户端已有统一错误提示层，也可在 ViewModel 中保留状态码，交给 UI 决定是空态、错误态还是登录引导。

## 5. 字段映射建议

建议客户端直接把服务端返回项映射为现有在线歌曲 `songData` 风格，尽量复用当前在线列表、推荐列表、播放页已有字段名。

推荐映射如下：

- `music_path` -> `musicPath`
- `path` -> `path`
- `path` -> `playPath`
- `title` -> `title`
- `artist` -> `artist`
- `album` -> `album`
- `cover_art_url` -> `cover`
- `cover_art_url` -> `coverUrl`
- `duration_sec * 1000` -> `durationMs`
- `false` -> `isLocal`
- `"online"` -> `sourceType`
- `source` -> `source`
- `source_id` -> `sourceId`
- `play_count` -> `playCount`
- `rank` -> `rank`

额外建议：

- `trackId` 可参考当前在线列表做 fallback 生成，不要求服务端单独提供
- 若 `title` 为空，可回退到 `music_path`
- 若 `artist` 为空，可回退为 `未知艺术家`
- 若 `cover_art_url` 为空，可回退到现有默认在线歌曲封面

### 5.1 与现有播放链路的关系

榜单歌曲点击播放时，应复用当前在线歌曲播放逻辑：

- 使用原始 `music_path/path` 去走现有在线播放地址解析
- 播放时继续保留原始在线 `music_path`
- 不要把榜单项转换成“本地歌曲模型”

### 5.2 与评论链路的关系

如果客户端已经接入在线评论功能，则榜单歌曲评论入口应继续使用原始在线 `music_path` 作为线程键。

也就是说：

- 服务端曲库歌曲直接用其相对路径
- Jamendo 歌曲直接用其虚拟路径

不要用标题、歌手或解析后的流地址反推评论线程。

## 6. 页面状态建议

### 6.1 加载态

首次进入榜单页时：

- 显示加载占位
- 禁止同时展示旧榜单数据和新周期 loading 文案混在一起

周期切换时建议：

- 保留当前列表直到新请求返回，或
- 进入局部 loading

二者择一即可，但不要出现“周期标签已切换、内容仍是旧榜”的无提示状态。

### 6.2 空态

只有在以下情况下显示空态：

- HTTP `200`
- `items=[]`

建议文案：

- `暂无热歌数据`

### 6.3 错误态

`503`：

- 显示 `榜单服务暂不可用，请稍后再试`

其他网络错误：

- 显示通用加载失败文案
- 保留手动刷新入口

### 6.4 登录态

热歌榜本身允许未登录浏览，因此：

- 页面加载不依赖登录
- 播放不依赖登录
- 收藏、加入歌单、评论等写操作仍遵守现有登录限制

## 7. 客户端实现落点建议

建议优先参考以下现有代码形态：

- `src/network/httprequest_v2.*`
- `src/viewmodels/MainShellViewModel*`
- `src/ui/widgets/library/recommend_music_widget.*`
- `qml/components/library/RecommendMusicWidget.qml`
- `src/ui/widgets/library/music_list_widget_net*`

推荐实现思路：

1. 在 `HttpRequestV2` 新增热歌榜请求与响应解析。
2. 在 `MainShellViewModel` 新增热歌榜透传信号与请求入口。
3. 在 `library` 域新增一个榜单页面组件，或在推荐页附近挂载一个独立榜单页。
4. 列表项操作直接复用在线歌曲现有动作：
   - 播放
   - 收藏
   - 下载
   - 加入歌单
   - 评论
5. 页面首屏默认请求 `30d + 20`，周期切换重新请求服务端。

## 8. 验收标准

客户端实现完成后，至少应满足：

- 能成功请求并展示 `GET /music/charts/hot?window=30d&limit=20`
- `7d / 30d / all` 切换后，列表会重新请求并刷新
- 榜单歌曲可以正常播放
- 榜单歌曲可以走现有收藏/下载/加入歌单逻辑
- `source=jamendo` 的歌曲可正常展示和播放
- `503` 会进入错误态，而不是渲染为空榜
- `200 + items=[]` 会进入真实空态
- 未登录用户可以浏览榜单，但写操作仍会走现有登录引导
